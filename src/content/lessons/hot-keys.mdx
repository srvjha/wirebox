At 19:00 sharp, tickets for a headline gig went on sale. Gatepass had eight booking partitions, all healthy, all sized the same. Seven of them sat near 5% CPU. The eighth, which held that one event's inventory, hit 100% and started timing out. Adding more partitions would have changed nothing. The problem was not the amount of data. It was one key.

## Skew and hot keys

Partitioning spreads *keys* evenly. It does not spread *traffic*. Real traffic follows a power law: a few keys get a huge share of requests, and most keys get almost none. The usual names:

- **Skew**: partitions carry unequal load.
- **Hot partition**: one partition carries far more than its share.
- **Hot key**: a single key so busy that one machine can't keep up, however you place it.

A hash function can't fix this. Every request for `event:headline-gig` hashes to the same place. The same applies to a celebrity's profile, a viral product, a live match score, or a global config row that every request reads.

Hot keys come in two flavours, and the cure differs:

- **Read-hot**: millions read, few write. A show's description page on sale day.
- **Write-hot**: many writers hit the same row. A seat counter or "tickets sold" number, incremented on every purchase.

## Find it before it finds you

You can't fix what you can't see. Per-partition averages hide this, because the other seven partitions pull the mean down. Look at:

- **Max versus median** load across partitions. A ratio above 2 or 3 is a warning.
- **Top-K keys** by request count in a short window, from a sampled counter or a streaming sketch (a count-min sketch uses a few kilobytes to find heavy hitters).
- **Per-key latency and error rate**, so the key behind a timeout storm shows up in a dashboard.

Also watch the *shape* over time. Some hot keys are predictable (a big on-sale is on your calendar). Others appear in minutes, after a tweet. Predictable ones can be prepared for. Surprise ones need automatic responses.

## Fixing read-hot keys

Reads are the easy case, because copies don't conflict.

**Cache in front.** A cache absorbs nearly all reads of a popular key. At 50,000 requests per second for the same event page, a cache with a 5-second TTL turns it into roughly one database read per 5 seconds per cache node. Add **request coalescing** so that on expiry, only one request goes to the database while the rest wait for its answer, avoiding a stampede.

**Replicate the hot key.** Keep extra copies on several nodes and let reads go to any of them. Some stores do this automatically, replicating a hot partition's data for reads only.

**Push it to the edge.** Static-ish content like descriptions and images belongs on a CDN, where it never reaches your partitions.

**Local in-process caches.** For the very hottest data, a tiny cache inside each application server with a 1 to 2 second TTL removes even the network hop.

## Fixing write-hot keys

Writes are harder, since every write must land somewhere and copies must agree. The central technique is to **split the key**.

**Key suffixing / sharded counters.** Append a small random number to the hot key (`sold:gig#0` to `sold:gig#9`). Each write goes to a random suffix, so ten partitions share the load. A read fetches all ten and sums them. You trade a read that is 10 times more expensive for writes that scale 10 times. Because hot-key reads are usually cached, this is a good deal.

**Pick the suffix by something useful.** Use the user id or the hour instead of random if you later want to query by it. Keep the suffix count small and known, or reads become a scatter-gather nightmare.

**Buffer and batch.** Don't update the shared row per event. Aggregate in memory for a short time (say 200 ms) and write one combined update: "plus 340" instead of 340 separate increments. You exchange a little delay for a large drop in write rate.

**Move the contention elsewhere.** For seat inventory, you can't just split the counter, since two buyers must not get the same seat. Instead, **pre-allocate**: split the 5,000 seats of the gig into 10 blocks of 500, each owned by one partition. A buyer is routed to a block. Contention drops 10-fold without breaking the one-seat-one-buyer rule. When a block runs out, the router moves buyers to the next.

**Queue it.** Put purchases in a queue for that event and process them in order from a single worker (see the queues module). The hot key becomes a steady drip instead of a spike, and the worker owns correctness.

## Don't forget the people

Some of the worst hot keys are really *hot tenants*. A single large organiser can account for half your traffic. A directory-based scheme lets you move that tenant to dedicated hardware. And a rate limiter per key or per tenant makes sure one noisy customer cannot take the whole fleet down.

<Callout tone="tip" title="Plan for the on-sale">
For events you know will be hot, don't wait for an alert. Warm caches, pre-split counters and pre-allocate seat blocks before the sale opens.
</Callout>

## Key takeaways

- Partitioning evens out keys, not traffic. One hot key can overload a partition no matter how many you add.
- Find hot keys by comparing max to median load and tracking top-K keys, not by looking at averages.
- Read-hot keys are fixed with caches, request coalescing, replicas and CDNs.
- Write-hot keys are fixed by splitting the key into sub-keys, batching writes, pre-allocating blocks or serialising through a queue.
- Some hot keys are hot tenants: isolate them and rate-limit them.
